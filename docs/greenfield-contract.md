# Behavioral and Operational Contract — "Coding-agent command safety gate"

This document describes WHAT a product must do, independent of any implementation. It was extracted from an existing product's observable behavior, documentation, tests, and operating constraints. It deliberately contains no source-tree, module, class, or function names. Where a behavior is marked **[compat]** it is something external parties (hosts, users, scripts) may depend on verbatim. Where marked **[essential]** it is core product behavior. **[safety]** marks a safety or security guarantee. **[ops]** marks an operational constraint. **[detail]** marks something observed that is probably an implementation choice, not a requirement. **[historical]** marks legacy behavior retained for migration. **[ambiguous]** marks behavior whose requirement status is unclear and should be validated.

---

## 1. Product purpose

**Problem.** AI coding agents (Claude Code, Codex, Cursor, Gemini CLI, GitHub Copilot CLI, Antigravity CLI, Grok Build, Hermes Agent, Kimi Code, OpenClaw, OpenCode, Pi, Amp) execute shell commands and file operations on a developer's machine. A helpful agent occasionally issues a command that destroys uncommitted work (`git reset --hard`, `git push --force`, `rm -rf` of the wrong directory, `find -delete`), or reads/writes secrets (`~/.ssh/id_rsa`, `.env`, `~/.aws/credentials`, the agent CLIs' own credential stores). Sandboxes do not stop these: a sandbox permits `git reset --hard` inside the project.

**Solution.** A local, offline, pre-execution gate that every supported agent host consults before running a tool call. The gate inspects the *intent* of the command text and the tool's file arguments, and returns allow or deny with an agent-readable explanation. It never executes anything, never sets OS permissions, never watches the network.

**Users.** Individual developers (single user, single machine), and teams who commit a project-scoped policy to git so every clone and cloud session is protected the same way. A secondary audience is tool authors who embed the check as a library.

**Major workflows.**
1. Tool-call gating (the hot path): host → gate → allow/deny, tens of times per minute.
2. Installation into one or more hosts; update; uninstall.
3. Policy authoring: safety preset, per-rule overrides, allow/deny paths, custom rulebooks (local or from GitHub), project-scope policy shared via git.
4. Diagnostics: "what is enforced right now", "why was this blocked", health check, audit log browsing, a local web dashboard.
5. Embedding: a library call that returns allow/deny for a command and cwd.

## 2. Actors and external systems

| Actor / system | Role | Trust |
|---|---|---|
| Coding agent (LLM) | Emits tool calls. Reads the denial text and is expected to follow its guidance. | **Untrusted.** The command text and tool inputs are adversarial in strict/paranoid mode, merely careless in standard mode. |
| Agent host CLI (13 of them) | Invokes the gate per tool call via a hook protocol; installs/registers the gate; may fail open or closed when the gate crashes. | Trusted to deliver the payload honestly; the execution context it reports (cwd, workspace roots) is trusted input. |
| Developer (user) | Installs, configures policy, reads diagnostics, approves project policy changes. | Trusted; the user's policy is authoritative. |
| Team lead | Commits a project-scope policy and rulebooks to a repository. | Trusted within the team (a hostile repo is out of scope; see residual risks). |
| Local filesystem | Policy files, rulebooks, audit logs, host config files, git metadata, symlinks. | Reads are trusted; symlinks and unusual namespaces are hazards. |
| Git repositories on disk | Determine protected metadata paths and linked-worktree status. | Read-only. |
| GitHub (api.github.com, raw.githubusercontent.com) | Source of official/team rulebooks during explicit `rule add/update` only. | Untrusted content, bounded fetch. |
| npm registry | Distribution; update-availability check in diagnostics. | Network optional; failure must be silent. |
| Host package/plugin stores | Where the gate's runtime lives after install (npm cache, host plugin dirs, a hosted git repo for one host). | Written by install only. |
| Library consumer | Node.js code calling the check function. | Trusted caller; must be told "if it throws, do not run". |
| Local web browser | Renders the dashboard against a loopback server. | Same-machine; token-gated. |

## 3. Capabilities

C1. **Decide** allow/deny for a tool invocation consisting of: host id, tool name, tool input (arbitrary JSON), execution directory, policy directory, session id. **[essential]**
C2. **Understand shell commands** in POSIX shells (bash/sh/zsh/dash/ksh/fish/csh/tcsh) and a conservative subset of PowerShell, including quoting, `&&`/`||`/`;`/`|`/`&`, subshells and brace groups, functions, heredocs, command substitution, variables, nested shells (`bash -c`), interpreters (`python -c`, `node -e`, ruby, perl), `eval`/`source`/`trap`, `env`/`sudo`/`command`/`builtin`/`busybox` wrappers, user-declared transparent wrappers, `xargs`, GNU `parallel`, `find -exec`, `awk system()`, `cd` effects, and env-assignment effects. **[essential]**
C3. **Recognize destructive operations** by a fixed catalog of built-in rules with stable public IDs (listed in §6.7). **[essential]**
C4. **Recognize sensitive-path access** across shell commands *and* the host's read/edit/write/grep/glob/patch tools, by a fixed catalog of secret rules with stable IDs (§6.7), plus user-configured deny paths and allow paths. **[essential]**
C5. **Protect the gate itself**: deny mutation of its own policy files, deny an agent invoking the privileged "apply project policy" command, and deny mutation of git metadata (`.git`, gitdir/commondir of linked worktrees and submodules, hooks directories). These run *before* policy is loaded and cannot be configured off. **[safety]**
C6. **Layer policy**: built-in defaults ← user policy ← project policy ← environment variables, with published precedence and with every project-scope weakening reported. **[essential]**
C7. **Safety presets** standard / strict / paranoid expressed as three capabilities (`fail_closed`, `paranoid_rm`, `paranoid_interpreters`) plus a `worktree_mode` workflow flag. **[essential]**
C8. **Custom rules** via rulebooks (two schema versions), local or vendored from GitHub, that can only ADD blocks and can override reasons or disable custom rules, never disable built-ins. **[essential]**
C9. **Degrade gracefully**: invalid or unreadable configuration never denies ordinary work; something protective is always enforced; the degraded state is reported on every surface. **[safety]**
C10. **Fail closed** on internal errors, resource-limit breaches, malformed host payloads, and unusable execution directories. **[safety]**
C11. **Audit** every decision (denials always; allows by default) to a local JSONL trail with secret redaction and retention. **[essential]**
C12. **Explain** a decision step by step, with redaction. **[essential]**
C13. **Diagnose** installation and configuration health, with machine-readable output. **[essential]**
C14. **Install / update / uninstall** into each of the 13 hosts, detecting what is installed. **[essential]**
C15. **Dashboard**: local web UI for activity review, policy editing (user and project draft), rulebook overview, integrations, and a false-positive report helper. **[essential, lower priority]**
C16. **Library API** for embedding. **[compat]**
C17. **Agent-facing skill/manual** shipped with the plugin, invocable only by the user. **[compat]**

## 4. End-to-end workflows

### W1. Tool-call gating (hot path)

**Trigger.** The host is about to run a tool. It either spawns the gate process with one JSON document on stdin (nine hosts) or calls an in-process handler (four hosts).

**Inputs.** Host-specific payload carrying: tool name; tool input (for shell tools a `command` string, optionally a per-call working directory; for file tools path-like fields; for patch tools a patch body); the session cwd and/or workspace roots; a session id; sometimes a transcript path.

**Validation (fail closed on each).**
- Raw stdin bounded to 8 MiB; overflow, empty, or non-JSON → deny "Failed to parse hook input JSON." / "Missing hook input JSON.".
- Payload must be a JSON object; tool name must be a non-empty string.
- Tool input traversal bounded: 64 nesting levels, 10,000 visited values, 10,000 own keys, 1 MiB per string, 4 MiB aggregate string data. Exceeding → deny without echoing the input.
- Execution directory must exist, be a directory, canonicalize (symlinks resolved), and for hosts that supply workspace roots, be inside a root. Windows UNC (`\\server\share`) and device namespaces (`\\?\`, `\\.\`) are rejected as *requested* cwds. Unusable → deny.
- An unsupported event name (e.g. a non-pre-tool event) → produce no output, exit 0.

**Decisions, in this fixed order** (each stage may deny; later stages never run after a deny):
1. Structural limits on the command string (input length 131,072 code units, 16,384 words, nesting depth 64) → deny "exceeds safe analysis limits".
2. **Own-policy-file protection**: if any write/edit/patch tool targets, or any shell operand, `=`-value, write redirection, `rm -r` of an ancestor, `mv` source, or `find -delete` root resolves (after `cd` tracking, simple variable tracking, `~`/env expansion, existing-symlink resolution) to the user policy file or the project policy file → deny with hard-stop intent and reason "This path contains the protected policy config and you must not modify or delete it."
3. **Apply-command protection**: if the command invokes the gate's own `policy apply` subcommand through any recognized runner spelling (direct binary, `npx`/`bunx`/`pnpx`, `dlx`/`exec`, versioned specs) → deny hard-stop.
4. **Git metadata protection**: if a move, a write redirection, or a write/edit/patch tool targets Git metadata → deny hard-stop "Git metadata and hooks are protected. Ask the user before modifying them." The protected set is per route, derived from the nearest ancestor `.git` entry of the cwd and of every tracked path: write/edit/patch tools cover the `.git` entry itself and every `hooks` subtree (the repository's, a linked worktree's, a submodule's); redirections cover the gitdir pointer file of a linked worktree or submodule and the `hooks` subtrees; a move destination covers the `.git` entry and the `hooks` subtrees; a move source covers the `.git` entry, the gitdir pointer file, the resolved gitdir/commondir, and the `hooks` subtrees, including through a trailing glob that can reach them. `rm -r` and `find -delete` reaching the same set are analyzer rules at stage 9 (`rm.git-metadata`, `find.delete-git-metadata`) that reuse the move-source test and carry a rule id.
5. **Load policy** for the policy directory (user file + project file + both scopes' rule configs + live rulebook files). This never throws for content reasons; it yields `ready` or `degraded` (§5, I4). Resolve effective safety capabilities from preset + overrides + env.
6. **Secret-path protection** (skipped only if the user policy disables it): collect candidate paths from the command (operands, assignment values, redirection targets, substitution bodies, piped `echo … | xargs reader`, piped scripts into interpreters, interpreter `-c/-e` string literals including base64-decoded ones, `curl -d @file`/`-F name=@file` uploads, `find` roots and `-exec` bodies, `awk` operands and `getline <`) or from the tool's path-like fields (`path`, `file_path`, `filepath`, `absolutePath`, `directory_path`, `notebook_path`, `target_file`, `search_directory`, `include`, plus `glob`/`pattern` for search tools) or from patch headers. Deny if any candidate matches a configured deny path (or descendant) — never relaxed — or a built-in secret rule not disabled and not covered by an allow path (allow paths never cover coding-CLI credential rules, anything under the gate's own config root, or home/above-home). In standard mode two relaxations apply to shell commands: (a) a standalone metadata-only check (`ls`, `stat`, `test -e|-f x`, `find` without action predicates; no pipes/redirections/substitutions) of a *built-in* sensitive path is allowed; (b) for `node`/`bun` inline code, string literals are inert data when the surrounding code has no filesystem/exec/require markers. Reason: "Access to a sensitive path is not allowed."; intent hard-stop; rule id reported.
7. Non-shell tools (path/patch/grep/glob/unknown routes) → **allow** here.
8. Empty or blank command on a shell route → deny (fail closed).
9. **Destructive-command analysis** of the command under the effective capabilities (§4 W1a). Deny with rule id, reason, intent, and the offending segment; else allow.

**Side effects.** One audit record per decision (denials always, allows when audit scope is `all`, which is the default; allows only for shell routes). Nothing else: no writes, no network, no cache.

**Outputs.** Host-specific allow/deny document (§6.2). The denial text is a fixed multi-paragraph frame (§6.5) that the agent reads. When policy was degraded, a `Config warning:` paragraph rides along on the next denial.

**Failure behavior.** Any unexpected exception inside stages 1–9 → deny with reason "… failed closed because command analysis failed unexpectedly. This is not caused by your command. Report it to the user." and intent stop-and-explain; an audit record carries the failure stage and an error class (path-canonicalization-limit, tool-input-limit, structural-shell-syntax-limit, unexpected-error). Debug detail to stderr only when a debug env flag is set. Two documented analysis budgets (path canonicalization, structural shell syntax) get the wording "exceeds safe analysis limits. Simplify or split the command and retry." instead.

**Observable signals.** stdout document; audit record; optional stderr debug line; exit code 0 in all handled paths (exit 1 only on an unhandled crash).

### W1a. Destructive-command analysis (within W1 step 9)

Given the command text, dialect hint (posix | powershell | auto), execution cwd, effective capabilities, worktree mode, the process environment snapshot (env map, home, tmpdir), a filesystem oracle (realpath, entry kind), and protected git metadata:

1. **Parse** into a program: sequence of simple commands, connectors, groups, function definitions; each word with expanded text, raw source, quoted flag, and provenance (literal | variable | command-substitution | arithmetic | glob | unknown); redirections with heredoc bodies; nested programs for substitutions and for live substitutions inside unquoted heredocs. Parse yields a status: complete | partial (e.g. unclosed quote) | invalid (bad heredoc, bad ANSI-C escape) | limited (budget hit). PowerShell dialect is selected explicitly or auto-detected from a genuine command-position cmdlet/alias (`Remove-Item`, `ri`, `del`, `erase`, `rd`, `rmdir`, `Get-Content`, `Set-Content`, `Add-Content`, `Copy-Item`, `Move-Item`, or `rm`/`cat`/`cp`/`mv`/`gc` with a PowerShell path expression) — quoted or commented mentions do not select it.
2. **Status handling.** limited → deny "exceeds maximum recursion depth / cannot be safely analyzed". invalid heredoc → standard: raw-text scan; strict: deny. Other invalid → deny in every mode. partial + strict → deny "could not be safely analyzed (strict mode). Simplify the command and retry, or ask the user to verify." partial + standard with unclosed quote → raw-text scan; other partial → structural analysis.
3. **Walk** the program tracking, per control-flow path: effective cwd (known only while every `cd`/`pushd`/`popd` provably returns to the original cwd; any real change makes cwd *unknown*, which makes relative `rm -rf` targets "outside cwd"), tracked env assignments (statement-level `NAME=v`, `export`, `unset`; seeded with `GIT_*`, `TMPDIR`, `IFS`), heredoc bodies written to files (so `cat > s.sh <<'EOF' … EOF; bash s.sh` analyzes the body), and function definitions (inlined on direct call). `&&` continues from success paths, `||` from failure paths, both retained across conditional chains; `&`, pipelines, and subshells isolate filesystem state. Substitutions are analyzed before their containing command. Paths are deduplicated and capped (64).
4. **Per simple command** (in this order; the first deny wins): strip leading assignments; peel wrappers (`sudo` incl. `-D dir`/`-i`, `env` incl. `-i`/`-u`/`-C`/`-S`, `command` (`-v` → `type`), `builtin`; bounded iterations); in strict, deny a dynamic executable (head from substitution/variable) and dynamic structure (substitution output before/in the option region of `git`/`find`/`rm`/`xargs`/`parallel`); unwrap user-declared transparent wrappers and re-analyze from the child; `eval`/`trap`: literal source recurses, dynamic source is denied except the standard-mode form `eval "$(single-literal-local-command)"` / `source <(…)` whose generator itself passes analysis and is not `curl`/`wget`/a shell; shell wrappers (`bash -c …`, `$SHELL -c`): `-n` is inert; `--rcfile`/`BASH_ENV`/`ENV` must be tracked heredoc files else deny in every mode; `-c` source recurses with positional parameters substituted from literal args; `bash file` recurses only if `file` is a tracked heredoc file; stdin sources (`bash < f`, `curl … | bash`) are literal only for `<<<'literal'` or a literal `printf`/`echo` producer — otherwise deny "shell execution source cannot be verified" in every mode (no rule id, not policy-filterable); `source`/`.` likewise; `awk`: literal `system("…")`/`"cmd" | getline`/`print | "cmd"` recurse, dynamic → deny; interpreters (`python*`, `node`, `ruby`, `perl`): a `-c/-e/--eval` code argument is denied outright under `paranoid_interpreters`, else recursed as shell (structural findings only) and text-scanned for destructive vocabulary outside string literals or inside literals when an exec sink (`system|exec|spawn|popen|subprocess|child_process|eval|fork|qx|backtick`) is present; a `node -e "console.log('…')"` print is exempt; `busybox X …` re-analyzes from X; device rules; then the head-specific rule sets for `rm`/`rmdir`, `git`, `find`, `xargs`, `parallel`, PowerShell `Remove-Item` family; for unknown heads, every suffix of the token list is tried as an embedded child command (so `myrunner git reset --hard` and `command -px git reset --hard` are caught) unless the head is on a display-only list (`echo`, `printf`, `cat`, `less`, `grep`, `rg`, …); finally custom rules.
5. **Rule semantics** (see rule IDs in §6.7). Highlights: `git reset --hard|--merge` with abbreviated long options (`--ha`); `git checkout` with `-f`, `--`, `--pathspec-from-file`, a ref plus a path, or ≥2 positionals (exempt `-b/-B/--orphan`); `git switch -f|--discard-changes`; `git restore` touching the worktree (exempt `--staged` alone, `--help`); `git clean -f` (exempt `-n/--dry-run`); `git rm -f` (exempt `--cached`, `--dry-run`); `git push --force|-f|+ref|--delete|-d|:ref|--mirror` (exempt `--force-with-lease`); `git branch -D|-d -f`; `git rebase --abort`, `merge --abort`, `tag -d`, `reflog delete|expire`, `stash drop|clear`, `worktree remove --force`; `GIT_SSH*`/`-c core.sshCommand` with a network subcommand; `-c alias.X=!…`, `GIT_CONFIG_COUNT` etc. aliases (count capped at 1,024; malformed count fails closed); `rm -r` (with or without `-f`) targets classified in order: IFS-unsafe `$TMPDIR` → outside; Windows namespace → outside; lexical root/home (`/`, `/*/*`, `/**`, `C:\`, UNC root, `~`, `$HOME`, `*` at home cwd) → catastrophic; canonical resolves to root/home → catastrophic; git metadata → catastrophic; trusted temp root (`/tmp`, `/var/tmp`, `/private/tmp`, `/private/var/tmp`, the OS tmpdir, `$TMPDIR/literal` when `TMPDIR` is a trusted temp) → allow; dynamic (contains `$`, backtick, glob, brace) → allow in standard, deny in strict; inside a user allow path (home-expanded, canonicalized, never inside home itself) → allow; cwd is home → deny; target is cwd itself (`.`, `./`) → deny; inside original cwd → allow (deny under `paranoid_rm`); else outside → deny. Symlinks are canonicalized so a symlink escaping cwd is "outside". `find … -delete` (exempt when every starting point is a trusted temp descendant), `find … -exec rm -rf`, `find` roots or `-name hooks` selecting git metadata; `dd of=/dev/…`, `mkfs /dev/…`, `shred anything`; `xargs rm -rf` with piped/`-I` input, `xargs` selecting a shell/interpreter/eval/find child from input; `parallel` template/`:::` expansion into any of the above, no-template stdin command streams, `--pipe`, remote `-S`, `--env`, custom `-I`, `{= =}` forms; PowerShell `Remove-Item` family with `-Recurse`/`-Force` prefix abbreviations (exempt `-WhatIf`), pipeline input under strict.
6. **Raw-text backstop**: when structure is unavailable (standard-mode unparseable input, single-word assignment segments like `W='rm -rf ~'; $W`, `env -S` strings, unsupported heredoc bodies, `parallel --env` values) the text is scanned linearly for destructive vocabulary (`rm -rf`, `reset --hard|--merge`, `clean -f`, `checkout -f`, `push --force|+ref|--delete`, `branch -D`, `tag -d`, `restore` without `--staged`, `find -delete`, `stash drop|clear`, `checkout --`, `dd of=/dev/`, `mkfs /dev/`, `shred`, download-piped-to-shell), skipping `echo`/`rg` prefixed lines → `raw-text.dangerous-command`, intent stop-and-explain. A quoted assignment that is only ever referenced as quoted data (`W='rm -rf ~'; echo "$W"`) is deferred (allowed) in standard.
7. **Heredocs**: a quoted-delimiter heredoc whose consumer is a message sink (`cat`, `tee`, `git apply`, `git commit`, `gh pr create`, `gh issue create`) is inert even if the body says `rm -rf ~`. An unquoted-delimiter heredoc with a live expansion and destructive text is denied. A literal interpreter heredoc (`python <<'EOF'`) is scanned as code.
8. **Rule filtering**: six catastrophic rules cannot be disabled by anything; the destructive master switch disables every other built-in; per-rule `on|off` overrides apply next; capability-gated rules (`fail_closed`, `paranoid_rm`, `paranoid_interpreters`) are on iff their capability is on, unless explicitly `on`; custom and raw-text findings bypass the filter.
9. **Worktree mode** relaxes only local-discard git rules (checkout/switch/restore/clean/rm/rebase/merge and `reset --hard` without a ref) when the cwd (after `-C`) is a verified linked worktree, no `GIT_DIR`/`GIT_WORK_TREE`/`GIT_COMMON_DIR`/`GIT_INDEX_FILE`, no `--git-dir`/`--work-tree`, no dynamic args, no `submodule.recurse` (command line, env, or effective git config — which may require asking `git config --get submodule.recurse` with a sanitized env), no `--recurse-submodules`, not `checkout -B -f`/`switch -C -f`, not `clean -ff`; never inside xargs/parallel/embedded contexts.
10. **Budgets** (each breach → deny stop-and-explain; the specific reason strings are [detail]): recursion depth 10; derived-command token budget 16,384; wrapper-peel iterations 20; control-flow paths 64; tracked heredoc files 64; parallel: 1,024 children / 16,384 tokens / 1 MiB / 16,384 replacements; path canonicalization: 16,384 realpath calls / 4 MiB candidate bytes / 256 missing suffix components; brace expansion of rm targets 64 alternatives / 16 KiB; git alias depth 5.
11. **Output**: allow, or deny {reason, intent (hard_stop | use_alternative | scope_down | manual_only | stop_and_explain; default manual_only), optional rule id, evidence = the offending segment text (with wrappers like `sudo` kept in the displayed segment)}.

### W2. Policy resolution (used by W1 step 5 and all diagnostics)

**Inputs.** User config root (`$CC_SAFETY_NET_HOME` or `~/.cc-safety-net`) and project directory (the policy directory from the invocation).

**Sources and precedence** (later layers override earlier where allowed):
1. Built-in defaults: level standard; worktree off; destructive protection on with no overrides and no allow paths; secret protection on with no overrides/deny/allow paths; audit retention 30 days.
2. User policy file `<root>/policy.json` **[compat]** (schema §6.3). Missing → defaults. Empty/malformed → built-in *protective* defaults (state degraded). Partially invalid → salvage: every recognized valid section survives, invalid ones fall back to protective defaults (degraded). Unknown fields → degraded warning. For one host (Amp) whose runtime may run on a remote machine, an embedded copy of the user policy stamped at install time substitutes for a missing user file.
3. Project policy file `<project>/.cc-safety-net/policy.json` **[compat]**: same schema minus `audit` (a project `audit` section is ignored with a warning). Scalars and `enabled` flags take the project value when set; per-rule overrides merge by id with the project winning its own ids; allow/deny path lists are unioned. A project MAY weaken the user policy; every weakening (lower level, disabled capability, worktree enabled, protection disabled, rule turned off that the user had on, added allow paths) is computed as a human-readable line and shown by status, doctor, statusline (🔻), GUI, and explain (`safetyPresetScope`). Malformed project file → user policy alone (degraded).
4. Rule configs `<root>/rules/rule.json` and `<project>/.cc-safety-net/rules/rule.json` **[compat]** listing rulebook sources, per-rule overrides (`off` or `{reason, intent?}`), and transparent wrappers. Each scope loads independently; a malformed `rule.json` drops that entire scope (including its transparent wrappers). Rulebook name collisions resolve user-first. A project override naming a user-scope rule is ignored with a warning. Unknown override keys warn. Transparent wrappers are unioned; reserved heads (shell names, wrappers) may not be declared as wrappers.
5. Rulebook files `<rules dir>/<name>/rulebook.json` **[compat]** (v1 and v2, §6.3), read live on every tool call. A source with no file, invalid JSON, a failed schema, a `name` mismatch, or an unvendored remote → that source dropped (degraded error). Rulebooks contribute only blocking rules. Custom rule ids are `<rulebook>/<rule>` and surface as `custom.<rulebook>/<rule>`.
6. Environment variables **[compat]**: `CC_SAFETY_NET_LEVEL=standard|strict|paranoid` raises but never lowers the level (a project file cannot lower an env-raised level); `CC_SAFETY_NET_STRICT=1|true` forces fail_closed; `CC_SAFETY_NET_PARANOID` forces paranoid_rm and paranoid_interpreters (not fail_closed); `CC_SAFETY_NET_PARANOID_RM`; `CC_SAFETY_NET_PARANOID_INTERPRETERS`; `CC_SAFETY_NET_WORKTREE`; legacy `SAFETY_NET_*` spellings consulted only when the new name is absent **[historical]**. Capability precedence: preset → policy `safety.overrides` → env flags. The effective level is `custom` when the three capabilities do not match a preset. Every surface shows the provenance of each capability (preset | capability_override | environment) with the contributing sources.

**Outputs.** An immutable effective policy plus state `ready` | `degraded {reason}` plus diagnostics, rule metadata (rulebook name/version, public source, reason override), and scope info (which scope supplied the level, weakening lines).

**Filesystem hygiene for policy/rule files** **[safety]**: reads of rule/rulebook files refuse symlinks at any component, verify the file did not change identity between open and read, and never leak paths or bytes in error messages; writes are atomic (temp + fsync + rename) with mode 0600 in 0700 directories. Duplicate readers must agree: the runtime, the GUI editor, the diff/apply command, and the audit-retention reader all see the same salvaged projection of a partially invalid user file.

### W3. Install / update / uninstall / detect

**Trigger.** User runs `install [--<host>]`, `update`, or `uninstall [--<host>]`.

**Detect** what is installed per host by reading host state files (never by running host commands that rewrite host state), e.g. Claude Code's installed-plugins record and settings `enabledPlugins`, Cursor/Antigravity/Grok/Kimi hook config files containing the exact managed command, OpenCode's plugin array, Pi's package list, Gemini's extension directory and enablement file, OpenClaw's extension directory (ownership header, manifest, byte-compare with the shipped bundle, enablement rules), Hermes' managed plugin files and config enablement, Copilot's version-gated hook files and plugin settings, Codex/Amp via their `plugin list` commands. Status per host: configured | disabled | not applicable | not inspected (unreadable).

**Install** (interactive multi-select picker on a TTY when no flag; exactly one flag otherwise; a non-TTY without a flag fails with exit 1): probe each host CLI's presence (`<cli> --version`, 5 s timeout) in parallel; then per selected host write the appropriate artifact **[compat: these exact artifacts must be found again by detect/uninstall]**:
- Claude Code: `claude plugin marketplace add kenryu42/cc-marketplace`, `marketplace update`, `plugin install cc-safety-net@cc-marketplace` (+ enable); the plugin's hook command is `node "${CLAUDE_PLUGIN_ROOT}/dist/bin/cc-safety-net.js" hook --coding-cli`.
- Codex: `codex plugin marketplace add|upgrade`, `codex plugin add cc-safety-net@cc-marketplace`; user must trust hooks in the host.
- Copilot: `copilot plugin marketplace add|update`, `plugin install`; flip `enabledPlugins["cc-safety-net@cc-marketplace"]` to true in `~/.copilot/settings.json` preserving JSONC text.
- Gemini: `gemini extensions install https://github.com/kenryu42/gemini-safety-net --consent` / update / enable.
- Cursor: add `{command:"npx -y cc-safety-net hook --cursor", timeout:30, failClosed:true}` to `hooks.preToolUse` in `~/.cursor/hooks.json` (`version:1`).

**Update** targets every *detected* host (including disabled), skips hosts whose CLI is absent, runs all in parallel, reports each independently, exit 1 if any failed; prints an "update available" nudge only for persistent (non-npx) installs.

**Uninstall** reverses each artifact precisely (host `uninstall`/`remove` commands; removal of only entries carrying the exact managed command; removal of only owned files).

**Outputs.** Per-host report lines; exit 0 (including cancel) or 1.

### W5. Library check **[compat]**

`checkCommand({ command: string, cwd: string }) → { kind: 'allow' } | { kind: 'deny', reason, ruleId? }`. Throws `TypeError` on a non-object, empty command, or non-absolute cwd. An unusable cwd yields a deny (fail closed). Re-reads policy on every call; writes no audit; touches no network; a thrown error means "do not run". The check is a shell-command route with dialect auto and the same cwd for execution and policy.

### W6. Audit trail **[compat]**

Location `<audit home>/.cc-safety-net/logs/<encoded cwd>/<YYYY-MM>/<YYYY-MM-DD>-<session>.jsonl` where audit home is `$CC_SAFETY_NET_AUDIT_HOME || $HOME || os home` (absolute), encoded cwd replaces non-alphanumerics with `-` (cap 180, `no-cwd`), and session id keeps `[A-Za-z0-9_.-]` (cap 128; empty → no write). Retention: after each append, at most once per UTC day, delete files whose whole UTC day is older than `audit.retention_days` (1–365, default 30, read directly from the user policy file so pruning works even when the rest is invalid); remove emptied directories; never follow symlinks; never throw. `CC_SAFETY_NET_AUDIT_SCOPE=blocked` records denials only; unset or `all` records allows too; any other value → denials only and a doctor warning.

## 5. Invariants

- **I1 [safety]** Own-policy-file, apply-command, and git-metadata protections run before any policy is read and cannot be disabled by any policy, level, override, allow path, or environment variable.
- **I2 [safety]** Six catastrophic rules (recursive delete of root/home in POSIX and PowerShell, deletion of git metadata by `rm`/`find`/`Remove-Item`) are enforced regardless of level, master switch, per-rule override, or allow path.
- **I3 [safety]** Configured deny paths (and descendants) are never relaxed by standard mode, allow paths, or metadata-only checks. Allow paths never cover coding-CLI credential rules, the gate's own config root, or home/above-home, and never apply to dynamic delete targets.
- **I4 [safety]** Invalid configuration never denies ordinary work, and never enforces the rejected values; something protective is always enforced; the degraded condition is reported on every surface (audit flag, denial warning line, status, doctor, statusline, GUI, `rule list`). A malformed user policy cannot turn secret protection off.
- **I5 [safety]** An environment-raised level cannot be lowered by any file. Every project-scope weakening relative to the user policy is visible.
- **I6 [safety]** Project rule configs cannot disable user-scope custom rules; user scope claims rulebook names first.
- **I7 [safety]** Any internal exception or breached resource budget during a decision yields a deny, never an allow, and never echoes an over-limit input.
- **I8 [safety]** Audit and diagnostic output never contain recognized credential forms; audit or pruning failures never change a decision.
- **I9 [essential]** The decision path performs no writes other than the audit append, no network, and no cross-call caching; policy is re-read on every decision (live rulebook edits take effect on the next call).
- **I10 [essential]** Decision ordering is deterministic and the first denying stage wins; later segments are not analyzed after a deny (explain reports them as skipped).
- **I11 [safety]** Rulebooks and custom rules can only add blocks or replace a custom rule's reason/intent; nothing in rule configuration can weaken a built-in.
- **I12 [essential]** Everyday developer commands (git status/add/commit/push/pull/log/diff/checkout -b/stash, npm/bun/pnpm/cargo builds, rg/grep/find -print, mkdir/mv/cp/touch/ls/cat/sed -n, `rm -rf node_modules|dist|build` inside the project) are allowed at standard AND strict.
- **I13 [compat]** Built-in rule ids, policy/rule/rulebook file schemas and versions, the audit record shape, the denial text frame and intent footers, CLI command names/flags/exit codes, the library API, env var names, and the host artifacts written by install are stable.
- **I14 [safety]** Hosts that fail open on a crashed hook receive an explicit allow or deny document for every handled call; adapter-internal failures are emitted as explicit denials.
- **I15 [safety]** The tool's own `policy apply` refuses to run without an interactive terminal.
- **I16 [ops]** A repository checkout of the project must be runnable as a plugin by `node <checkout>/dist/bin/cc-safety-net.js` with no package-manager install step (four hosts load plugins from git checkouts).

### 6.8 Threat model and accepted residual risk (governs what NOT to build)
Standard mode protects helpful, non-adversarial agents from accidents; it is not bypass-proof against crafted syntax and must never block everyday commands. Strict/paranoid fail closed on anything unverifiable and are for prompt-injection/adversarial contexts. Accepted residual families (do not add parser fidelity to close them; add strict-mode fail-closed instead): dynamic executables and computed names; structure assembled through substitution; unverifiable recursive-delete targets (`rm -rf "$BUILD_DIR"`); runtime-reconstructed strings inside interpreter code; script/interpreter file bodies (`bash setup.sh`); exact glob/brace/IFS expansion emulation; aliases/functions/PATH/IFS mutation at runtime; quoting-concatenation tricks; exact `find`/`xargs`/`parallel`/archive emulation; standalone metadata-only checks of sensitive paths in standard; adversarial repo-delivered project policy; laundered writes to the policy file through `git`; live rulebook edits losing enforcement; vendored rulebook drift; the GUI token being readable by the launching agent. Never residual: catastrophic protections failing in any mode; strict/paranoid failing open where documented closed; false positives on common safe commands; resource-bound regressions (catastrophic regex backtracking, unbounded recursion); secret leakage in outputs.

## 7. Non-functional requirements

| Requirement | Evidence / value |
|---|---|
| **Latency** [ops] | One gate invocation per tool call. For nine hosts this is a fresh Node process (`node dist/bin/cc-safety-net.js` or `npx -y …`): startup + parse + policy load + analysis must stay well under the hosts' 30-second hook timeouts and be imperceptible in practice (target: tens of milliseconds of work after startup; a 90 KB safe command must explain within seconds). No persistent daemon exists or is expected. |
| **Throughput** | Single-user, interactive; tens of calls per minute. No concurrency between calls is required; concurrent hosts on one machine may append to distinct audit files. |
| **Memory/CPU** [safety] | Bounded by the input caps above; no unbounded recursion; no catastrophic regex; pathological inputs (deep nesting, 16k words, 8 MiB payloads, 1,025 git config entries) must terminate quickly with a deny. |
| **Scale** | Policy files are small (≤64 rulebook sources, ≤1,024 rules each). Audit logs grow by one line per tool call and are pruned by retention. |
| **Reliability** [safety] | Fail closed on internal error; never fail open. Never lock the user out on bad configuration (degrade). Audit failures never affect decisions. |
| **Recoverability** | Every degraded condition names the file, the fallback, and the repair on every surface; `doctor` finds quiet regressions (dropped rule sources). Atomic writes for every owned file. |
| **Security** [safety] | No network on the decision path; symlink-refusing policy reads; UNC/device path rejection; 0600/0700 files; secret redaction in all outputs; loopback-only GUI with token; `policy apply` TTY-gated; no arbitrary code from rulebooks (fixtures never executed); one bundled dependency, no third-party shell parser. |
| **Auditability** | JSONL trail with stable fields, per-session files, retention, suspect detection, machine-readable diagnostics. |
| **Portability** [ops] | Windows, macOS, Linux; Node ≥ 18 (no Bun at runtime); PowerShell dialect; MSYS drive paths (`/c/…` → `C:/…`); per-platform temp roots; Windows `.cmd` shims for host probes. |
| **Deployability** [ops] | npm publish with provenance; git-checkout plugins (dist committed); marketplace plugin manifests; per-host install artifacts; update path that defeats npx caching. |
| **Observability** | `status`, `doctor --json`, `explain --json`, `logs --json`, statusline glyphs, GUI, debug env flag on stderr. No telemetry. |
| **Maintainability** | Single maintainer today; heavy CI (lint, typecheck, dead-code, duplication, ≥90% line/function coverage, packed-tarball verification on a 6-cell matrix, randomized e2e reruns). Explicit review rules discourage adding parser emulation to chase crafted bypasses. |
| **Extensibility** | Demonstrated axes of change: new agent hosts (13 so far, added roughly monthly), new built-in rules (field incidents), new secret patterns, new rulebook sources, new safety capabilities (rare). Not demonstrated: third-party code plugins, remote/multi-tenant operation, alternative storage. |
